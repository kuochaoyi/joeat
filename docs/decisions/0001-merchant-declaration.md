# 決策紀錄 0001:店家聲明(Merchant Declaration)

日期:2026-11-02。範圍:店家自填功能的產品與資料決策,以及這一輪實作了什麼。
背景設計:[merchant_self_declaration_design.md](../merchant_self_declaration_design.md)。

## 定位

> **店家聲明是風險資訊來源,不是行銷工具。**

後果:聲明只影響(1)能不能通過硬限制、(2)警示層級、(3)可解釋性;**不影響排名分數**;不做「填得越完整越容易被推薦」的誘因;介面用語是聲明事實,不是保證。

## 決策

| # | 決策 | 來源 | 狀態 |
|---|---|---|---|
| D1 | **人工審核,不做自動核准。** 只有 strong 驗證能產生「確認不含 / 確認含有」(`CONFIRMED_*`);basic 驗證最多產生「可能」(`LIKELY_*`),過不了硬限制的「已確認」。strong 的方法限定為:**電話回撥、實地確認、官方菜單 + 人工覆核**。每筆聲明至少記錄:驗證者、驗證時間、驗證方式、證據來源 | 你的建議 | **已實作**(資料庫約束 + 審核 API) |
| D2 | **用語**:不用「安全」「保證無過敏原」「100% 無花生」。範例:「店家於 2026/11/02 聲明其目前菜單未使用花生;共用設備資訊:未知。」「依店家提供資訊,目前未確認含有花生。」 | 你的建議 | **已實作**:結果頁與 LINE 回覆以「店家於 YYYY/MM/DD 聲明…;共用設備資訊:…」的事實陳述呈現聲明,測試守住不含禁用詞 |

### D3 的調整:分類屬於「限制」,不屬於「屬性」

你建議把屬性分成 `safety_constraint` / `preference_constraint`(花生過敏 → 安全型;不吃牛 → 偏好型)。**我改成依「每位成員為什麼避開它」決定**,因為同一個屬性可以兩者皆是:對魚過敏的人「不吃海鮮」是安全型,單純不愛吃的人是偏好型;因宗教不吃牛的人也不是偏好型。

- `ref.constraint_reason.constraint_class`:`allergy`、`medical`、`religion` → **safety**;`belief_diet`、`dislike` → **preference**。
- 成員沒說原因(`unspecified`)時,才用 `ref.attribute.default_constraint_class`:過敏原(花生、堅果、甲殼類、牛奶、蛋、芝麻、大豆、麩質)與無麩質 → safety;其餘(牛、豬、海鮮、內臟、生食、素食、純素、清真)→ preference。
- 函式 `ref.effective_constraint_class(reason, attribute)` 已實作並有測試。
- **`religion → safety` 已確認(2026-11-04,產品負責人)**:信仰上的禁忌通常連共用鍋具都在意,所以視為嚴格。若之後要改成偏好型,只需改 `ref.constraint_reason` 的一列資料,並更新 `test_constraint_class_comes_from_the_reason_then_the_attribute_default` 裡的預期。
- 目前 UI 只會替過敏原自動帶 `allergy`,其他項目沒有「原因」選項,因此現在除過敏原外都會落在偏好型。要讓使用者能表達「這個我是因為健康 / 宗教」需要補 UI。

## 整合後的行為(推薦整合,第 5 步)

引擎在決策矩陣(30 列)查到結果之後,多做兩個**以成員為單位**的調整。其餘規則沒變。

### 1. 偏好型限制:「有些餐點含有」只降為警示(D3)

條件**全部**成立才會從「排除」降為「注意(high)」警示:

- 這位成員的限制是**偏好型**(原因是 `dislike` / `belief_diet`;沒填原因時用屬性預設,如牛、豬、內臟);
- 屬性**不是 critical**(花生、堅果等關鍵過敏原永遠不放寬,即使成員自己選了「不喜歡」);
- 限制是「不吃」型(avoid);
- 店家聲明 `presence_extent = some`(只有些餐點含有),證據狀態是 `CONFIRMED_PRESENT` 或 `LIKELY_PRESENT`。

`most`、範圍未知(第三方證據沒有範圍)、安全型限制(過敏 / 醫療 / 宗教)、「必須有」型限制,仍照矩陣排除。降級的檢查列在稽核資料裡標 `engine_note = softened_some`,結果頁的狀態是 `partial_conflict`(「店家表示只有些餐點含有不想吃的食材」),警示寫「可選擇不含的餐點,建議向店家確認」。

### 2. 嚴格過敏模式(新,使用者自選)

成員在限制頁勾選後(只有選了過敏原才會出現),**他自己的安全型「不吃」限制**只有在 `CONFIRMED_ABSENT` 時才通過:`UNKNOWN`、`LIKELY_ABSENT`(包含「店家聲明沒有,但共用設備可能 / 未知」)都改為排除,排除原因寫「{屬性}:沒有店家確認」。

- 只影響勾選的那位成員自己的安全型限制;別人的限制、他自己的偏好型限制都不變。
- 結果頁只說「有成員開啟了嚴格過敏模式」,**不說是誰**(群組很小時仍可能被推測,這和既有的排除原因同等級)。
- **用現有的真實資料,嚴格模式幾乎一定是 0 家**,因為目前沒有任何真實店家提供確認資料。畫面會如實說明並建議改回一般模式或聯絡店家,**不會硬湊推薦**。

### 3. 用語與 `possible` / `unknown` 的區分(D2、D4)

| 情境 | 結果頁怎麼說 | 警示等級 |
|---|---|---|
| 沒有任何資料 | 「{屬性}資訊不足,建議向店家確認」 | 依矩陣 |
| 店家聲明沒有,共用設備**可能**共用 | 「店家聲明菜單未使用,但共用設備可能有交叉接觸,建議向店家確認」 | 同矩陣(critical 屬性為 critical) |
| 店家聲明沒有,共用設備**未知** | 「店家聲明菜單未使用;共用設備資訊:未知,建議向店家確認」 | 同上 |
| 店家聲明沒有,共用設備確認無共用,且 strong 驗證 | 聲明陳述(見下)+ 通過 | 無 |

聲明一律以**帶日期的事實陳述**顯示(`店家於 2026/11/04 聲明其目前菜單未使用乳製品;共用設備資訊:確認沒有共用。已由揪呷人工驗證身分。`),未達「已確認」的會加「尚未列為『已確認』」。陳述由結構化欄位(日期、共用設備、範圍、是否 strong 驗證)產生,**不是**直接轉貼證據文字(那裡面有驗證者名字)。聲明從不改變警示等級、也不加分。「已知資料中沒有發現衝突」「資訊不足(不代表安全)」這類否定句保留。

### 4. 共用設備對發布狀態的影響(發布時,第 3 輪前就有)

對「關鍵過敏原」(`risk_level = critical`,即花生、堅果、甲殼類、牛奶、蛋、芝麻、大豆、麩質)且店家答「菜單完全沒有」時,發布的狀態由共用設備決定:

| 共用設備 | 發布的證據狀態 | 引擎的結果(一般模式) | 嚴格模式 |
|---|---|---|---|
| `confirmed_none` | `CONFIRMED_ABSENT`(strong 驗證時) | 通過,顯示聲明陳述 | 通過 |
| `possible` | `LIKELY_ABSENT` | 重要警示 | 排除 |
| `unknown` | `LIKELY_ABSENT` | 重要警示 | 排除 |
| `confirmed_shared` | `LIKELY_PRESENT` | 排除該店 | 排除 |

**不確定共用設備的過敏原聲明,對過敏的使用者沒有實質好處**(效果等同「資訊不足」,只是措辭更具體)。這是 D4 的直接後果。需要在試辦時觀察店家實際上會不會回答「確認無共用」;若多半答「不確定」,這個功能對過敏族群的價值就很有限。非關鍵屬性(牛、豬、海鮮…)的共用設備只存不降級。

### 5. 「回報錯誤」(限流、不自動生效)

- `POST /restaurants/{id}/reports`:只有加入過聚餐的人(`participant_id` 當憑證)、而且該店出現在**自己這場聚餐的結果裡**才能回報。
- 限流(資料庫計算):每人 24 小時最多 3 次、同一店同一項不能重複回報、每家店最多 30 筆待處理。
- **回報不會改變任何推薦結果。** 它只進審核佇列;審核者「駁回」或「升級為事故」。只有升級才會(對過敏反應 / 資訊錯誤)暫停該店的正向聲明——所以不能用回報去打掉競爭對手的聲明。審核者看不到回報人是誰,只看到「此店待處理的不同回報人數」。
- **已知限制**:參與者很容易建立(新聚餐、新 LINE id),所以這些限流擋得住隨手濫用,擋不住有心人;真正的防線需要真實的 LINE 身分。

### 5.1 撤下已發布的聲明(試辦前補上,遷移 0006)

試辦準備時發現缺口:店家**沒有任何方式撤下已發布的聲明**(撤銷認領只改認領狀態,不會讓證據失效;事故只能硬湊)。現在 `POST /ops/declarations/{id}/withdraw`:原則與緊急煞車一致——**正向聲明(「沒有 X」)立刻失效,風險資訊(「含有 X」)保留到原有效期限**,因為拿掉它會讓使用者更不謹慎。聲明本身不刪除(歷史保留)。

### 5.2 聲明日期(遷移 0007)

給用餐者看的「店家於 X 聲明」,X 是**店家切結的日期**(`attested_at`,台灣時間),不是審核者發布的日期。證據文字同時分開寫聲明日 / 驗證日 / 菜單日期,並**不再包含審核者名字**(餐廳詳情是公開 API);驗證者仍記錄在認領與稽核紀錄。只影響之後發布的聲明。到期日仍從發布日起算。

### 6. 刻意沒做的

- SQL 版參考引擎(`product.evaluate_session`)**沒有**跟進這兩個調整:它仍是 v1 規則,與 Python 引擎的比對測試只涵蓋不涉及這些調整的情境。正式路徑只用 Python 引擎。
- 目前 UI 除過敏原外沒有「這個我是因為健康 / 宗教」的原因選項,所以實際上只有過敏原會是安全型;宗教 / 醫療型要補 UI。
- 聲明的有效期限到期提醒、一鍵續期、附件上傳(第 4 步剩下的部分)。
