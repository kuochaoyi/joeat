# 營運手冊(審核者每天做的事)

審核後台:`<前端網址>/ops`。登入需要 `OPS_API_KEY` 和你的名字(稽核紀錄用)。**名字想用代號也可以**(例如 `reviewer-a`),系統只要求至少 2 個字;不要把店家的姓名寫進任何欄位。

## A. 每家店的標準流程

1. **邀請**(`認領與驗證` → 邀請餐廳):搜尋店名 → **不要勾「示範用認領」** → 建立邀請 → **立刻複製連結**(只顯示一次,資料庫只存雜湊,忘了只能撤銷重發)。
2. **驗證**(同頁,該列「驗證」):只記**你實際做的事**。
   - `電話回撥`(強):你撥公開電話、接電話者自稱老闆 / 店長並能代表店家。
   - `實地確認`(強):你人在店裡、跟負責人當面確認。
   - `官方菜單 + 人工覆核`(強):你對照店家官方的菜單看過;**發布時必須有菜單連結**。
   - `官方管道訊息`(基本):只有店家的官方 LINE / FB 回覆。**基本驗證永遠只能產生「可能」,不會是「已確認」。**
   - 備註(至少 5 字)用**職稱**描述,**不寫姓名 / 個人電話**。
3. **傳連結**(驗證**之後**,話術見 [03_call_script.md](03_call_script.md))。
4. 店家填寫、送出 → `聲明審核` 的「待審」出現。
5. **審核**(見 B)。
6. 發布後**回報店家**,並在日曆記下**第 75 天**(聲明 90 天到期)的續期提醒。

## B. 審核一份聲明時看什麼

打開 `聲明審核` → 該筆「審核 →」。從上往下:

1. **驗證區塊**:方式、等級、備註對得起來嗎?(例:備註寫「電話回撥」但方式選「官方管道訊息」→ 先釐清)
2. **發布預覽表**:這是「按下發布會寫入什麼」。逐列看:
   - 「寫入狀態」是否合理?`共用設備降級` 表示店家答「菜單完全沒有」但共用設備不是確認沒有 → 只會是「可能」。
   - **可疑的答案模式**:八種過敏原全部「完全沒有 + 確認沒有共用」、卻是一家明顯會用到的店(牛肉麵店答「沒有牛肉」、甜點店答「沒有蛋奶」)。直接**退回補件**並打電話問。
   - 菜單日期太舊(系統只收 180 天內)、或跟菜單連結內容對不上。
3. **矛盾的既有證據**(紅色列):店家說「沒有 X」但我們有第三方(部落格 / 媒體)說「可能有 X」。
   - 先**打電話問清楚**:是菜單改了、還是我們的來源錯了?
   - 確定第三方資料過時 → 勾「我已查證,同意取代」再發布(留稽核)。**沒查證過不要勾。**
   - 與「已確認」的證據矛盾 → 系統**不讓你發布**,代表需要人工處理資料,先別硬壓。
4. **決定**:`核准並發布` / `退回補件`(附具體問題) / `駁回`(附原因)。退回與駁回的說明系統要求至少 5 字。

## C. 店家來電說菜單改了 / 要撤下

`聲明審核` → 「已核准」→ 該筆 → **撤下這份已發布的聲明**(說明至少 5 字,用職稱)。
- 「沒有 X」類聲明**立刻失效**(這家店對 X 回到「資訊不足」);
- 「含有 X」類風險資訊**保留到原有效期限**(拿掉會讓使用者更不謹慎),稽核紀錄會寫保留了幾筆;
- 撤下後店家用**原連結**可以重新填寫(連結還在有效期內的話;過期要重新邀請)。

## D. 使用者回報 / 事故

- **有人說吃了出現過敏反應**(不論從哪裡聽到):**先登錄、再調查**。`事故` → 登錄 → 類型「過敏反應」。系統會**立即暫停**該店所有正向聲明(「沒有 X」),不用等查證。暫停是可逆的:
  - 查完沒問題 → 「駁回(恢復聲明)」;
  - 屬實 → 「確認(作廢並撤銷認領)」。
  - 然後打電話給店家。
- **一般回報**(`使用者回報` 分頁):回報**不會自動生效**,也看不到回報人。看「此店待處理的不同回報人」:1 個人說資訊有誤、還是 5 個人。查證(電話)→ 填處理說明(至少 5 字)→ **升級為事故**(會暫停聲明)或**駁回**。
- 每天至少看一次這兩個頁面。**事故沒處理完之前,那家店的正向聲明不會恢復。**

## E. 每天 / 每週

| 頻率 | 做什麼 |
|---|---|
| 每天 | `聲明審核` 待審、`使用者回報` 待處理、`事故` 未結案 |
| 每週 | `python scripts/pilot_metrics.py` 看漏斗與共用設備答案分布;更新試算表 |
| 第 75 天 | 傳到期前提醒給店家(話術在 03);**到期是手動提醒,系統不會通知任何人** |
| 第 90 天 | 聲明到期:系統自動不再採用(`valid_until`),店家對該屬性回到「資訊不足」 |

## F. 資料與隱私

- 我們存:餐廳公開資料、店家的聲明答案、驗證方式 / 日期 / 備註(職稱)、審核者名字(稽核)。**不存**店家老闆的姓名、個人電話 / LINE。
- 店家要求刪除:**聲明不能刪除(設計如此,保留歷史)**,但可以**撤下**(C)——撤下後不再顯示給使用者。如果有法律上的刪除要求,需要你另外處理資料庫(這是人工、有風險的操作,先備份)。
- 備份:試辦資料庫請**每天 `pg_dump`**(見 05)。`seed.py --reset` 會刪除一切——它現在**拒絕**在已有真實認領的資料庫上執行,除非加 `--destroy-real-data`;**不要在試辦資料庫上用那個旗標**。

## G. 出事了怎麼辦

| 狀況 | 做法 |
|---|---|
| 不確定某筆聲明對不對,但已經發布 | 先撤下(C),再查。撤下是可逆的(店家可重填) |
| 連結不小心傳錯人 | `認領與驗證` → 該列「撤銷」,重新邀請 |
| `/ops` 打不開 / 金鑰外洩 | 換 `OPS_API_KEY`、重啟後端;`/ops` 在換金鑰前就是任何知道金鑰的人都能操作 |
| 資料庫異常 | 停止邀請新店家,先還原備份;已發布的聲明仍然是資料庫裡的資料,別在沒備份時動它 |
