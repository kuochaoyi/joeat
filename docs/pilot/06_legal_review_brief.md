# 法務審閱簡報:店家聲明

> **給律師的版本**。目的:請你審閱下列所有「店家看到的」與「用餐者看到的」文字,回覆可核准的版本與需要補的文件。
> 製作者不是律師。「我們的觀察」是整理出來的線索,**不是法律結論**。引用的文字都是系統現在的實際內容(附檔案位置),不是改寫過的。
> 現況:切結文字標示為**未審閱草稿**(`attest-v0-draft`),店家頁頂端會顯示「不可正式上線」橫幅;預檢程式把這一項列為阻擋項。

## 1. 產品與事實(律師需要先知道的)

**是什麼**:「揪呷」是 2–20 人聚餐的決策工具。每位成員私下填「不能吃 / 過敏」等硬限制,系統排除違反的餐廳、排名、給 Top 3 與理由。**店家聲明**是試辦中的功能:店家說明自己菜單的過敏原與食材,經我們人工審核後,在結果裡以一句有日期的話呈現給用餐者。

**目前只在高雄鹽埕區,試辦規模預計 6 家店。沒有任何真實店家或使用者使用過。**

| 事實 | 說明 |
|---|---|
| 驗證方式 | 人工。強驗證 = 電話回撥公開電話 / 實地確認 / 官方菜單 + 人工覆核;基本 = 官方管道訊息。**我們驗證的是「接電話的人能代表店家」,不是菜單內容的真偽** |
| 展示給用餐者的內容 | 「店家於〔日期〕聲明其目前菜單未使用花生;共用設備資訊:〔…〕」這類事實陳述,附「已驗證」標示。**不使用「安全 / 保證 / 100% / 無過敏原 / 零過敏」(程式有測試守住)** |
| 對推薦排名的影響 | **沒有**。聲明只影響能否通過硬限制、警示等級、可解釋性,不加分 |
| 費用 | 不收費、不承諾曝光 |
| 有效期限 | 聲明預設 90 天(上限 180 天)到期自動不採用;店家可隨時請我們撤下,撤下後「沒有 X」類聲明立即失效 |
| 緊急煞車 | 營運登錄「過敏反應 / 資訊錯誤」事故後,該店所有「沒有 X」類聲明**立刻暫停**(不先通知店家),查證後恢復或作廢 |
| 使用者回報 | 用餐者可回報資料錯誤(含自由文字 ≤ 300 字);**不會自動改變任何結果**,由審核者決定 |
| 聲明刪除 | 聲明**不可刪除**(保留歷史與稽核),只能撤下 |
| 會員 / 登入 | 試辦期間用戶端自報身分(`AUTH_MODE=dev`);LINE 登入尚未啟用 |

**我們儲存的個人相關資料**(與下方第 3 節問題對應):

| 資料 | 內容 | 備註 |
|---|---|---|
| 店家聲明人 | 身分類別(老闆 / 店長 / 員工)、切結版本、切結時間 | **不存姓名**。驗證備註要求寫職稱,不寫姓名與個人電話(營運規定,系統無法強制) |
| 驗證紀錄 | 方式、時間、備註、驗證者(審核者自填名字或代號) | 審核者名字會出現在稽核紀錄 |
| 店家連結 | 一次性邀請連結(只存雜湊)、30 天有效 | 傳連結用的 LINE / 簡訊**不存** |
| 用餐者 | LINE 使用者與群組 id **只存雜湊**;**顯示名稱(≤20 字)存在 `participant.label`,並顯示給同一場聚餐的其他成員**;個人的過敏 / 飲食限制 | 限制不會顯示給其他成員,只以「某項條件排除」的群組層級呈現 |
| 使用者回報 | 回報人(僅用於限流,審核者看不到)、類型、關聯項目、自由文字 | **自由文字可能含健康資訊(例如描述過敏反應)** |
| 保存期限 | 目前**沒有**自動刪除:聚餐 7 天後只是「不能再加入」,資料仍在 | 需要律師與你決定保存與刪除政策 |

## 2. 文字清單(逐字)

### A. 店家端

**A1. 填寫前導言**(`core/merchant_form.py` 的 `intro`;`m/[token]/page.tsx`)
> 請依「目前的菜單」回答。不確定就選「我不確定」,這是完全正常的答案,不會有任何影響。
> 您的回答會經過揪呷團隊審核後才會顯示給顧客,並有效 90 天。

**A2. 切結文字**(`ATTESTATION_TEXT`,版本 `attest-v0-draft`;`{role}` 為老闆 / 店長 / 員工)
> 我是這家店的{role}。上述資訊適用於「本分店、目前的菜單」(菜單日期:{menu_as_of})。我了解顧客可能依這些資訊決定是否用餐,並同意在菜單或廚房作業改變時更新。
> ☐ 我已閱讀並同意上述內容

**A3. 預覽(店家送出前看到「顧客會看到什麼」)**(`describe()`)
- 確認不含:「店家於 {日期} 聲明其目前菜單未使用{項目};共用設備:{確認無共用}。」
- 共用設備未確認:「依店家提供資訊,目前未確認含有{項目}(不列為「已確認」:共用設備尚未確認無共用);共用設備:{可能共用 / 未知}。」
- 含有:「店家聲明{部分 / 大部分}餐點含有{項目}。」
- 共用設備確認共用:「店家表示{項目}雖不在菜單上,但與其他餐點共用設備;系統會把這家店視為可能含有{項目}。」
- 未作答:「沒有回答的項目(「我不確定」)不會顯示任何聲明,顧客會看到「資訊不足」。」
- 「是否列為「已確認」取決於我們對您身分的驗證方式與共用設備的回答。」

**A4. 狀態訊息**
- 未驗證:「等待身分確認:我們的團隊會先與您聯絡確認身分,完成後您就可以填寫。」
- 已送出:「已送出,等待審核:我們會審核後與您聯絡。審核通過後,顧客才會看到您的聲明。」
- 已通過:「已通過審核:您的聲明自發布日起有效 90 天;菜單有變動時請聯絡我們更新或撤下。」(此句已於本次修正,原文為不通順的「有效至 90 天內」)

**A4b. 入座需求兩題(新)**:「客人可以帶寵物入內用餐嗎?(室內座位;只有戶外座位可以,請在備註說明)」選項:可以 / 不可以 / 我不確定。「你們親子友善嗎?(有兒童座椅或兒童餐)」選項:有 / 沒有 / 我不確定。預覽與用餐者看到的句子:「店家於 {日期} 聲明可攜帶寵物入內 / 不可攜帶寵物入內 / 提供兒童座椅或兒童餐 / 未提供兒童座椅與兒童餐。」另附「已由揪呷人工驗證身分」或「尚未列為「已確認」」。**店家說「不可以」時,攜帶寵物的聚餐會排除這家店**,請一併審閱。

**A5. 共用設備題**:「「{項目}」:廚房是否與其他餐點共用鍋具、炸油或工作檯?」選項:確認沒有共用 / 可能有共用 / 確定有共用 / 我不確定。

**A6. 營運對店家的口頭說明**:[03_call_script.md](03_call_script.md)(含「不是認證也不是保證」「不影響排名」「可隨時撤下」「不記您的姓名」等承諾)。**這些口頭承諾也請一併審閱**。

### B. 用餐者端

**B1. 免責聲明**(結果頁、LINE 回覆;`schemas/api.py`、`line_bot.py`)
> 推薦只依據目前蒐集到的資料。標示「資訊不足」的項目代表我們無法確認,不代表安全;過敏或嚴格飲食請務必向店家確認。

**B2. 店家聲明陳述**(`recommendation/explain.py`)
- 標籤:「店家聲明・已驗證」或「店家聲明」。
- 〔日期〕一律是**店家切結(按下同意)的日期**,不是審核者發布的日期。
- 確認不含:「店家於 {日期} 聲明其目前菜單未使用{項目};共用設備資訊:{確認沒有共用}。**已由揪呷人工驗證身分。**」
- 未達已確認:「店家於 {日期} 聲明其目前菜單未使用{項目};共用設備資訊:{未知}。**尚未列為「已確認」。**」
- 含有:「店家於 {日期} 聲明其菜單{有些餐點 / 大部分餐點}含有{項目}。…」
- 推薦理由:「有店家聲明並經人工驗證:{項目}」

**B3. 警示句**
- 資訊不足:「{項目}資訊不足,建議向店家確認」
- 店家聲明沒有但共用設備可能:「{項目}:店家聲明菜單未使用,但共用設備可能有交叉接觸,建議向店家確認」
- 共用設備未知:「{項目}:店家聲明菜單未使用;共用設備資訊:未知,建議向店家確認」
- 只有些餐點含有(偏好型限制):「{項目}:店家表示有些餐點含有,可選擇不含的餐點,建議向店家確認」
- 第三方資料:「{項目}:資料顯示可能含有(未確認),建議向店家確認」(**來源為部落格 / 媒體 / 品類推測,指名特定餐廳**)

**B4. 嚴格過敏模式**(限制頁)
> 嚴格過敏模式:我的過敏很嚴重,只推薦店家已聲明並確認不含的餐廳。沒有店家確認的都會被排除,所以可能完全沒有結果。其他人看不到是誰開的。

結果頁:「有成員開啟了「嚴格過敏模式」:他的過敏項目只推薦店家已聲明並確認不含的餐廳,沒有店家確認的都會被排除。」

**B5. 回報**:「回報會交給審核人員查證,在查證前不會改變推薦結果。每人 24 小時內最多回報 3 次。」

**B6. 限制頁**:「系統只能依「已知資料」判斷;餐廳資料不足時會明確標示「資訊不足」,不會假裝安全。過敏請務必再向店家確認。」

**B7. 餐廳詳情**:「本頁資料來自公開來源,未經店家確認。」「目前沒有任何過敏原或飲食項目有第一手的「確認不含」資料;沒有列出的項目代表資料不足,不代表安全。」

## 3. 請律師回答的問題

**店家端**
1. **誰能切結?** 現在可選「老闆 / 店長 / 員工」。員工是否有權代表店家作菜單的聲明?要不要只開放老闆 / 負責人?要不要留下可識別身分的方式(目前刻意不存姓名)?
2. **切結內容是否足夠?** 現在只有一段話。是否需要:「就我所知屬實」的聲明、同意內容公開顯示給不特定用餐者、聲明期限與撤回權、錯誤時的責任歸屬(店家 vs 平台)、平台不審查菜單真偽的說明?
3. **「已同意」的證據力**:我們留存切結版本、時間、身分類別與勾選(沒有 IP / 裝置)。是否足夠?需要簽章或書面嗎?
4. **試辦要不要簡易書面約定**(而不是只靠電話與切結)?內容建議包含什麼?
5. **電話口頭承諾**(不收費、不影響排名、可隨時撤下、不記姓名、90 天到期)是否構成約定?該如何在文字上落實?

**用餐者端**
6. **「已驗證」是否會被誤讀?** 我們驗證的是**身分**,不是**內容**;現在寫「已由揪呷人工驗證身分」。是否需要更明確(例如「我們沒有查驗菜單實際內容」)?
7. **過敏族群的合理信賴**:B1 的免責聲明是否足夠?嚴格過敏模式的文字(「只推薦店家已聲明並確認不含」)是否可能被理解成保證?平台對重度過敏者有無額外注意義務?
8. **對特定餐廳展示第三方推測**(B3 最後一項,來源部落格 / 媒體 / 品類推測,例如「麩質:可能含有」)是否有商譽或不實資訊風險?措辭要怎麼調整?
9. **食品標示與廣告**:店家聲明或平台的呈現,是否可能被視為食品標示或廣告而適用相關規範?試辦階段要避開什麼?

**資料與營運**
10. **個資**:顯示名稱(LINE)、過敏 / 飲食限制(健康相關)、回報自由文字(可能描述過敏反應)是否屬需特別處理的資料?需要的告知、同意與保存 / 刪除政策?現況是**沒有自動刪除**。
11. **「聲明不可刪除」與刪除請求**如何並存?撤下是否足以回應?
12. **緊急煞車**:登錄事故後**立即暫停**該店聲明,且不先通知店家。程序上是否需要通知 / 申訴機制?「確認事故」會撤銷認領,店家是否有救濟途徑?
13. **使用者回報**的濫用(對競爭對手):由審核者決定、有限流。是否還需要其他保護?
14. **營運人員的名字**會進稽核紀錄。是否需要內部規範?
