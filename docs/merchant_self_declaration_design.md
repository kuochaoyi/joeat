## 1. 為什麼做

資料可行性 PoC 與 MVP 都指向同一個缺口:**30+ 家店裡沒有任何一家有「確認不含」的第一手資料**。所以每個推薦的過敏原都只能顯示「資訊不足」,「嚴重過敏模式」也無法推薦任何已確認的店。公開網頁、OSM、稅籍都無法提供這種資料,因為「沒看到」不等於「沒有」。**唯一能產生「確認不含」的路,是店家自己說,並且負責。**

**目標**:讓推薦池中的店,能對 17 個屬性提供有期限、可追溯、可撤銷的第一手聲明,並由現有引擎直接使用(`CONFIRMED_ABSENT` → 通過並可顯示「已有第一手資料確認」)。

**非目標**(本階段):菜單品項層級資料、自動 OCR 菜單、店家登入與帳號系統、付費方案、點餐、廣告。

## 2. 設計原則

1. **沉默仍是 UNKNOWN。** 每一題預設「不確定」,**絕不預設「沒有」**,也不預勾。「不確定」是合法答案,不影響任何東西。
2. **只有被驗證過的人,才能產生 `CONFIRMED_*`。** 驗證弱的聲明最多是 `LIKELY_*`。
3. **聲明是整份快照。** 新聲明取代舊聲明;沒重新提出的屬性回到 UNKNOWN(測試 F1)。避免舊答案在菜單改版後悄悄留存。
4. **聲明會過期。** 預設 90 天、上限 180 天;過期自動失效,不需要任何排程(view 已用 `valid_until` 過濾)。
5. **矛盾不靜默解決。** 與既有證據衝突時:`LIKELY_*` 需具名審核者明確覆蓋(留稽核紀錄);`CONFIRMED_*` 一律擋下(測試 D1–D6)。
6. **人在迴路。** 沒有「自動核准」:發布需要具名審核者。
7. **有緊急煞車。** 一則過敏事故或錯誤通報,立刻暫停該店的「正向(安全)聲明」,由人工決定(§8)。
8. **不因為填寫而加分。** 聲明本身不進計分(避免鼓勵亂填)。它只透過「證據狀態」影響硬限制判斷。
9. **措辭是「店家聲明」,不是「安全」。** 介面不使用「安全」「無過敏原」等詞,並附共用設備與「仍請告知店員」。
10. **歷史不可竄改。** 稽核紀錄 append-only;聲明不可刪除(只能撤回)。

## 3. 角色與信任模型

| 角色 | 能做什麼 | 驗證 |
|---|---|---|
| 店家聲明人(claimant) | 開邀請連結、填聲明、提交、之後續期 | 見下 |
| 營運 / 審核者(operator) | 發邀請、驗證店家、審核並發布、處理事故 | 內部帳號(目前沒有後台,見 §13) |
| 消費者 | 看到聲明結果;**通報**錯誤或事故 | 無需驗證(可匿名) |

### 為什麼不能「搜尋店名 → 我是老闆」
店名、地址、電話、統編**都是公開資料**,知道它們不能證明你有權代表這家店。如果任何人都能認領,競爭對手可以替別人亂填,惡意者可以替一家含花生的店填「完全沒有」。

### 驗證等級(`merchant.claim.verification_level`)
> **方法已改(決策紀錄 0001)**:strong = 電話回撥 / 實地 / 官方菜單覆核;basic = 官方管道訊息;「營運認識」已移除。下表是最初草案,僅供對照。

| 等級 | 驗證方式 | 可產生的證據 | 風險 |
|---|---|---|---|
| `none` | 只有邀請連結,尚未驗證 | **不能提交**(`status ≠ verified` 時 `start_declaration` 直接拒絕) | — |
| `basic` | 官方管道訊息(例如從店家官方 FB / IG / LINE 帳號私訊確認) | 最多 `LIKELY_*`(中信心) | 帳號可能被盜或由工讀生管理 |
| `strong` | 電話回撥到公開電話並由接聽者確認、營運人員實地到訪、或營運人員認識業者本人 | 可產生 `CONFIRMED_*`(高信心) | 電話號碼有人接就會通過;**接聽者不一定有權代表店家** |

資料庫約束:`verified` 必須有方法、驗證人與時間;`strong` 只能搭配回撥 / 到訪 / 營運已知(**用官方管道訊息不能成為 strong**,測試 A2、A3)。

**現實限制**:電話回撥要有電話。PoC 中樣本只有 50% 有電話。沒有電話的店只能走實地到訪或官方管道訊息。

### 邀請流程(目前建議)
1. 營運在後台(或腳本)為某 `restaurant_id` 建立 `claim`,產生一次性 token(**只存 SHA-256**,原文只顯示一次),連結寄給店家。
2. 營運**另外**完成驗證並把 claim 標成 `verified`(等級與方法必填)。連結本身不代表驗證。
3. 店家開連結,用 LINE 登入(綁定 hash 後的 LINE id、聲明人角色)填寫。

## 4. 流程與狀態

```
   operator            merchant                                   operator                      system
   ────────            ────────                                   ────────                      ──────
 invite(token) ─►  open link / LINE login
 verify (call/visit)                          ┌─ needs_info ◄─────────┐
        │                                     ▼                       │
        └──► claim: verified ──► draft ──► submitted ──────► review ──┼─► approved ─► publish ─► first-party evidence
                                 (17 items,   (attested,               │                           (valid 90d)  ──► engine uses it
                                  all not_sure) menu date)             └─► rejected                    │
                                                                                                    ├─ expires → UNKNOWN (automatic)
                                                    consumer incident report ─► kill switch ─► suspended ─► operator resolves
```

宣告狀態:`draft → submitted → (needs_info ↔ submitted) → approved | rejected | withdrawn`;`approved → withdrawn` 允許;其他終態不可回頭(資料庫 trigger 強制)。

**續期**:到期前 30 天提醒(通知尚未實作)。續期 = 提交一份新的完整聲明(未來可做成「菜單沒變,一鍵確認」,仍會產生新的聲明與稽核)。菜單變動後商家應重新提交,否則舊聲明到期才失效——這是已知風險(§14)。

## 5. 店家看到的表單

**原則**:白話、一頁一組、手機優先、5 分鐘內完成、不要求店家懂「屬性代碼」。

### 題目(逐項對應 17 個屬性)

| 分組 | 白話題目 | 選項 | 內部屬性 → 答案 |
|---|---|---|---|
| 過敏原(8) | 「你們的**菜單**裡,有任何餐點使用到 **花生**(含花生粉、花生醬、花生油)嗎?」(堅果、牛奶、蛋、芝麻、大豆、麩質、甲殼類同格式) | 完全沒有 / 有些餐點有 / 大部分餐點有 / 我不確定 | `absent_entire_menu` / `present_in_some_dishes` / `present_in_most_dishes` / `not_sure` |
| 食材(6) | 「菜單裡有 **牛肉 / 豬肉 / 海鮮 / 內臟 / 生食** 嗎?」 | 同上 | 同上 |
| 飲食(4) | 「你們有提供 **素食 / 全素 / 清真 / 無麩質** 的餐點嗎?」 | 有 / 沒有 / 我不確定 | `offered` / `not_offered` / `not_sure` |
| 每個過敏原後追問 | 「這項食材,廚房是否與其他餐點**共用鍋具、炸油或工作檯**?」 | 沒有已知共用 / 可能共用 / 不確定 | `cross_contact` |
| 清真 | 認證編號(選填;**有編號才可能成為「已確認」**) | 文字 | `certificate_ref` |
| 附件 | 菜單連結或照片(選填;有的話證據基礎為「官方菜單」) | URL / 檔案 | `menu_url` / `menu_file_ref` |

### 切結與預覽
- 切結(版本化,存 `attestation_version`):「我是這家店的 ○○(老闆/店長/員工),上述資訊適用於**本分店目前的菜單**(菜單日期 YYYY-MM-DD)。我了解顧客可能依此決定是否用餐,並同意於菜單變動時更新。」**確切文字須法務審閱。**
- 預覽:「顧客將看到:**店家於 2026-11-02 聲明菜單不含花生(共用設備:可能)。有效至 2027-01-31。**」並顯示「已確認」或「LIKELY」的差別。
- 聲明人角色(owner / manager / staff)進入稽核與證據文字。

### 答案如何變成證據(已測試)

| 項目 | 答案 | `strong` 驗證 | `basic` 驗證 |
|---|---|---|---|
| avoid(過敏原、食材) | `absent_entire_menu` | `CONFIRMED_ABSENT`(HIGH);有菜單附件則基礎為 `official_menu` | `LIKELY_ABSENT`(MEDIUM) |
| avoid | `present_in_some_dishes` / `present_in_most_dishes` | `CONFIRMED_PRESENT`(HIGH) | `LIKELY_PRESENT`(MEDIUM) |
| require(素食等) | `offered` | `CONFIRMED_PRESENT`;**清真沒有認證編號只能到 `LIKELY_PRESENT`** | `LIKELY_PRESENT` |
| require | `not_offered` | `CONFIRMED_ABSENT` | `LIKELY_ABSENT` |
| 任何 | `not_sure` | 不寫入證據(= UNKNOWN);並使該屬性先前的第一手聲明失效 | 同左 |

每筆證據:來源 = 第一手、`applies_to = this_branch`、`observed_at = 菜單日期`、`last_verified_at = 發布日`、`valid_until = 發布日 + valid_days`、證據文字含聲明人角色、日期、共用設備與備註。現有的資料庫規則照常檢查(不符會被擋)。

## 6. 資料模型(`draft_0003_merchant_declaration.sql`)

| 物件 | 用途 |
|---|---|
| `merchant.claim` | 誰能代表哪家店:token(雜湊)、驗證方法 / 等級 / 驗證人 / 時間、聲明人 LINE(雜湊)與角色、30 天過期 |
| `merchant.declaration` | 一份聲明:狀態、有效天數(1–180)、菜單日期、菜單附件、切結版本與時間、審核者與時間。**複合外鍵 `(claim_id, restaurant_id)`:一個 claim 只能替它自己的餐廳聲明** |
| `merchant.declaration_item` | 17 列,每列一個屬性的答案 + 共用設備 + 備註 + 認證編號;提交後凍結;答案必須符合屬性類型(trigger) |
| `merchant.declaration_audit` | append-only 稽核(建立、每次狀態變更、覆蓋第三方證據),含操作者 |
| `merchant.incident_report` | 通報:過敏反應 / 資訊錯誤 / 其他;可匿名 |
| 既有表的變更 | `restaurant_attribute_evidence` 新增 `status`(active / superseded / suspended)、`superseded_by`、`declaration_id`、`suspended_by_incident`;`v_evidence_valid` 只計 `active`;新增一條合法配對 `(LIKELY_ABSENT, restaurant_declaration)` |
| 函式 | `start_declaration`(只有 verified 的 claim,17 項全為 not_sure)、`submit_declaration`(菜單日期限 180 天內)、`publish_declaration`(核准 + 寫證據 + 矛盾檢查)、`resolve_incident` |

**不需要改**:硬限制規則矩陣、計分、推薦引擎。現有的 `CONFIRMED_ABSENT → PASS 且可顯示已確認` 路徑由新資料自然啟動(測試 C2)。

## 7. 審核規則

**資料庫強制(不依賴審核者記得)**:未驗證的 claim 不能聲明;答案與屬性類型相符;提交後凍結;核准需要具名審核者與切結;`CONFIRMED_ABSENT` 需第一手、HIGH、此分店、180 天內;聲明不可刪除;稽核不可改。

**審核者要看的**(目前沒有後台,需要自己查資料庫):

1. 是否與既有證據矛盾。`publish_declaration` 會**擋下**並列出證據編號:
   - 對 `LIKELY_*`(例如媒體寫「土豆粽」但店家聲明沒有花生):審核者查證後以 `p_supersede = true` 明確覆蓋,稽核紀錄記下是誰。
   - 對 `CONFIRMED_*`(例如店名「牛肉麵」確認含牛):**永遠擋下**,不能用聲明覆蓋。先處理資料,或駁回聲明。
2. 「完全沒有」是否合理:例如店名是海鮮粥卻聲明「完全沒有海鮮」,應直接駁回(目前靠人看;可加規則)。
3. 菜單日期是否合理、附件是否真的是這家店的菜單。
4. 抽查:定期電話複核一定比例已發布的聲明(目前只是建議,沒有機制)。

## 8. 防濫用與緊急煞車

| 威脅 | 對策 | 狀態 |
|---|---|---|
| 冒名 / 競爭對手惡意填寫 | 只有營運驗證過的 claim 能提交;token 只存雜湊、30 天過期、可撤銷 | 已有資料模型;token 發放後台未做 |
| 為了好看亂填「完全沒有」 | 不因填寫加分;矛盾擋下;具名審核;稽核;抽查 | 部分(抽查未做) |
| 員工不知情、答錯 | 聲明人角色入稽核與證據文字;建議 owner / manager 簽核(§15 待決定) | 未決定 |
| 菜單改了沒更新 | 90 天預設有效期;菜單日期必填;到期提醒 | 提醒未做 |
| 已發布後出事 | **煞車**:通報過敏反應 → 立刻暫停該店**所有正向聲明**;資訊錯誤(可指定屬性)→ 暫停該屬性。由審核者 `resolve_incident`:駁回 → 恢復;確認 → 被暫停的證據永久作廢,並**撤銷該店所有已驗證的 claim**(需重新驗證才能再聲明)(測試 G1–G7) | 資料模型已驗證;通報入口(使用者介面)未做 |

**煞車只暫停「正向(安全)聲明」**:不含某物、或提供某需求。「含有某物」的聲明不會被暫停——暫停它會讓店看起來更安全,方向相反(測試 G2)。

## 9. 對推薦與介面的影響

- **引擎不變**。證據狀態 → 既有決策矩陣。
- **結果卡片新增(建議文案,待法務)**:`店家於 {日期} 聲明菜單不含花生 · 有效至 {日期} · 共用設備:可能。過敏請務必告知店員。` 既有的 `confirmed_safe` 欄位會開始有內容;**仍不使用「安全」一詞**。
- **「嚴重過敏模式」**(建議,需要產品決定):只推薦「所有 critical 限制都是 `CONFIRMED_ABSENT`」的店。**能推薦幾家完全取決於聲明覆蓋率**;覆蓋不足時介面要誠實說「目前只有 N 家有店家聲明」,不得偷偷放寬。
- **「回報錯誤」入口**:結果頁每家餐廳提供,寫入 `incident_report`(§8)。
- **語意缺口(重要)**:目前聲明是**餐廳層級**。`present_in_some_dishes` 會變成 `CONFIRMED_PRESENT`,引擎因此**排除**該店(測試 C5、C6)。對**過敏**這是保守且正確的;但對**口味類**限制(不吃牛)會過度排除:一家牛肉、雞肉都有的店,不吃牛的人其實點雞肉就行。解法是**菜單品項層級**資料(哪幾道菜含什麼),讓群組判斷「這家有沒有足夠多每個人都能吃的菜」。這是 Phase 2,需要重新設計規則與資料,**本設計不處理**。

## 10. 隱私與法律(未驗證,非法律意見)

- **個資**:聲明人以 hash 後的 LINE id 識別(不存原始 id);不蒐集真名;餐廳電話是公開資料。通報人可匿名。
- **保存**:聲明與稽核**保留**(歷史不可刪,用於事故追查);證據依 `valid_until` 失效但不刪。是否需要保存期限與刪除權,須依個資法評估。
- **責任**:需由律師確認(1)切結文字與服務條款如何分配「業者對菜單資訊負責、平台僅彙整與顯示」;(2)平台在業者聲明錯誤造成傷害時的責任;(3)對外宣稱用語的界線;(4)通報事故的處理義務。**我沒有查證相關法規,這裡只是列出需要問的問題。**
- 「已確認」只代表**店家聲明且經我們驗證了聲明人**,不代表我們檢驗過廚房。

## 11. 商家動機與冷啟動(誠實的部分)

**店家為什麼要填?我不知道。** 這是整個功能最大的未驗證假設。可能的誘因:顧客願意去「資訊完整」的店(對有過敏需求的團體是硬需求,他們可能只會去有聲明的店)、免費、之後的曝光。但**不能**用「填了就加分」來誘導(原則 8)。建議 Phase 0 先用人工陪同 5–10 家,實際觀察:願不願意、會不會填、填得準不準、花多久。

## 12. 分期

| 階段 | 內容 | 退出條件(建議) |
|---|---|---|

## 14. 已知風險與限制

1. **沒有真實使用者驗證**:所有流程都是設計與資料庫層的驗證。
2. **電話回撥的信任上限**:接聽者不等於有權限的人。
3. **聲明與菜單脫節**:90 天內改菜單而沒更新,舊聲明仍有效。可考慮較短預設或強制複核。
4. **餐廳層級語意**(§9):`present_*` 一律排除,對口味類限制過度保守。
5. **共用設備資訊目前只是備註**:引擎不使用它做決定;「完全沒有」+「共用設備:可能」的組合仍顯示為已確認,只是附註。這是否可接受要由產品與法務決定。
6. **通報可被濫用**:惡意者可以用假通報暫停對手的聲明。需要限流與審核,並考慮要求通報帶聯絡方式(但那會降低通報意願)。
7. **PostgreSQL 16.2 單一實例驗證**;無併發測試(同時發布與同時通報)。
8. **沒有後台**:審核與發 token 現在只能直接操作資料庫 / 腳本。
